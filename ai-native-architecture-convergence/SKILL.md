# AI Native 产品架构收敛

目标不是追求理论完备，而是形成**权威清楚、主链可执行、异常可恢复、足以进入产品和技术实现**的架构基线。

## 1. 建立本次收敛契约

开始前先明确：

- 当前要支持的近期产品、技术或商业决策；
- 当前阶段是探索、模块收敛、历史回溯、完成关闸，还是架构转产品；
- 哪些材料是权威正文、版本边界、历史实现、外部知识或用户陈述；
- 实际阅读深度与尚未核验范围；
- 本次明确不做什么；
- 文件、Git、外部系统或生产动作是否已经获得独立授权。

缺少会改变结论的必要信息时，只询问最低必要内容。已有明确上下文时直接推进，不让用户重复提供事实。

## 2. 按任务加载工作模式

只读取当前任务需要的参考文件：

- 新议题、复杂模块或范围不清：读取 [决策域构建](references/decision-domain-builder.md)。
- 涉及 Agent、自主执行、权限、事实或写回：读取 [权威与分层审计](references/authority-and-layer-audit.md)。
- 涉及跨模块流程、状态、版本、失败或恢复：读取 [Handoff 与生命周期审查](references/handoff-and-lifecycle-review.md)。
- 回看旧文档、已确认决策或判断是否重开：读取 [历史决策审计](references/historical-decision-audit.md)。
- 核心模块准备 Accepted、冻结或关闭：读取 [对抗式完成闸门](references/adversarial-completion-gate.md)。
- 架构已确认，需要形成信息架构、用户旅程或 PRD 边界：读取 [架构转产品基线](references/architecture-to-product-baseline.md)。
- 涉及跨任务、跨会话、跨阶段或跨项目连续性，或需要个性化、知识复用、上下文压缩：先判断是否确有长期连续性需求；成立时读取 [记忆与上下文架构](references/memory-and-context-architecture.md)。
- 需要形成稳定、可交接的架构产物：按需读取 [轻量输出契约](references/output-contracts.md)，只使用当前任务需要的模板。

多个模式可以组合，但不要为了形式加载全部参考文件。

## 3. 共享收敛主线

1. **定义对象与粒度**：先说明正在讨论的是方向、领域对象、版本、任务、动作、页面投影还是实现组件。
2. **建立完整决策域**：先覆盖问题空间，再按依赖、风险、价值、复杂度或验证成本排序；局部优先项不得冒充全部范围。
3. **区分权威与判断**：明确谁观察、谁拥有事实、谁提出候选、谁校验、谁能写入和谁承担责任。
4. **贯通主链与 Handoff**：检查输入、适用版本、责任转移、外部副作用、失败出口和恢复路径。
5. **拆开正交维度**：生命周期、公开状态、执行状态、权限、风险和证据等级不得压成一个万能状态。
6. **补齐时间与异常**：检查失败、超时、不响应、取消、结果未知、争议、删除、恢复和历史版本。
7. **判断连续性需求**：检查任务是否需要跨任务、会话、阶段或作用域延续信息；需要时专项设计记忆与上下文，不需要时不扩张记忆系统。
8. **划分 V1 承载方式**：分别判断必要业务能力、最轻产品承载、确定性系统、Agent 辅助、人工兜底和当前版本不做的高级能力。
9. **设置停止线**：剩余问题能由实现、人工、沙箱、灰度或真实运营验证解决时，停止扩张逻辑架构。

具体场景默认用于识别问题类别、解释和压力测试。除非已有权威封闭枚举，不得用持续追加场景代替分类与规则。

## 4. 标明结论强度

每项重要输出明确属于哪一种：

- `verified_fact`：当前证据可以直接支持的事实；
- `accepted_decision`：用户或权威流程已经确认的决策；
- `complete_decision_domain`：覆盖当前议题的决策维度，不等于功能穷举；
- `object_mainline`：主要对象和关系，不宣称覆盖全部异常；
- `closed_enum`：允许直接实现为受控枚举；
- `extensible_classification`：可增加类型，但扩展受 Policy、Schema 或版本流程控制；
- `illustrative_scenario`：解释或压力测试示例；
- `implementation_pending`：逻辑已确认，具体实现待技术设计；
- `external_validation_pending`：必须通过供应商、法规、沙箱或真实运营验证；
- `out_of_scope`：当前版本明确不做。

不要使用“完整、全部、已完成、已上线”等词，除非已经说明对应对象、范围和完成标准。

## 5. 输出要求

根据任务规模选择最低充分输出，通常包括：

- 近期用途、范围、证据和阅读深度；
- 完整决策域与讨论顺序；
- 核心对象、权威、版本和责任；
- 主路径、关键 Handoff 与失败恢复；
- V1 最小承载、人工兜底和后置能力；
- 已确认、待确认、待实现、待外部验证和不做事项；
- 停止线与下一阶段。

关系复杂时优先使用适合的流程图、状态图、时序图、关系图或责任矩阵。每张图只回答一个主要问题，图后说明作用域和未表达内容。

## 6. 三个检查时点

- **结论形成前局部反推**：新分类或关键结论首次提出时，立即检查覆盖、责任、校验、持久化、扩展和未知兜底。
- **模块完成闸门**：走查业务、用户、Agent、数据、生命周期、Handoff 和跨模块影响，并执行对抗式审视。
- **完成前不确定性复盘**：检查低置信度判断、外部假设、过早完成声明和未保留的取代关系。

三者不能互相替代。发现实质缺口时先修正或降级完成状态，不用“已经讨论”代替完成。

## 7. 权限与项目边界

本 Skill 提供分析、审计和交付结构，不授予文件修改、Git、依赖安装、外部系统写入或生产操作权限。执行动作前继续遵守当前项目的授权闸门和权威文档。

项目特定对象、状态、套餐、Agent 名称和支付规则应保留在项目权威正文中；本 Skill 只规定如何分析、校验和收敛，不预设具体答案。

## 8. 基于证据演进

不要因为单次失败或新场景就继续扩写主指令。先判断问题属于项目特例、宿主能力限制，还是跨任务重复出现的通用缺口。

修改正式规则前：

1. 用 [行为评测案例](evals/cases.md) 复现问题；
2. 说明改动解决什么失败，以及不改变什么边界；
3. 对相关既有案例做回归，避免提高一种任务表现却破坏另一种任务；
4. 只有重复且稳定的领域差异才建立可选 Domain Pack，不把项目知识写入通用入口；
5. Skill 可以提出改进候选，但正式 Prompt、权限、评测和版本仍需人类审核发布。

评测关注可观察行为和架构不变量，不要求固定措辞、固定标题或统一篇幅。
