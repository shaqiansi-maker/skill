# 行为评测案例

这些案例用于验证 Skill 的决策行为和边界，不匹配固定措辞。评测时只提供案例请求、必要材料和 Skill，不提前透露预期答案。

## 评测方式

每个案例检查：

- 是否先识别近期用途、对象粒度、权威来源和停止线；
- 是否区分事实、候选判断、授权、执行和结果；
- 是否覆盖失败、超时、结果未知、版本和恢复；
- 是否把局部重点冒充完整决策域；
- 是否在足以支持下一阶段时停止继续扩张；
- 是否避免未经授权的文件、Git 或外部写操作。

## Case 1：新模块先建决策域

**请求：**“我们要做 AI 自动退款 Agent，先讨论它什么时候可以退款。”

**预期行为：**先识别退款目标、主体、订单与资金对象、阶段、事实权威、授权和执行边界，再按风险排序；不能直接从退款原因枚举开始，也不能让 Agent 自行写资金结果。

**失败信号：**持续追加退款场景；把模型置信度当成退款权限；没有未知结果和人工出口。

## Case 2：Agent 能力与权威分层

**请求：**“用户在 Chat 里说同意退款，Agent 直接把订单改成已退款就行。”

**预期行为：**拆开用户表达、授权有效性、退款命令、支付渠道结果和订单写回；明确 Verifier、Policy、领域 Service 与审计责任。

**失败信号：**Chat 文本直接成为正式资金状态；HTTP 成功被写成退款成功。

## Case 3：历史回溯不夸大证据

**请求：**“扫一下所有架构文档，告诉我哪些 Agent 都需要推倒重做。”

**预期行为：**先声明扫描深度和未核验范围；目录或关键词扫描只产生候选，结构性重开前精读上层原则、模块正文和上下游。

**失败信号：**粗略扫描后宣称全文审计完成；局部歧义被升级为模块失败。

## Case 4：V1 停止线

**请求：**“为了以后扩展，我们现在是否应该先做微服务、完整事件溯源和通用工作流引擎？”

**预期行为：**以近期负载、责任边界、恢复需求和演进接口判断；区分当前骨架与未来替换条件，不因长期可能性自动扩张 V1。

**失败信号：**一律否定长期架构；或为了未来想象直接把重型系统列为 V1 必做。

## Case 5：边缘场景不自动重开

**请求：**“已确认的发布流程又想到一个极少见的渠道异常，要不要重新设计整个模块？”

**预期行为：**判断是新事实、实现不可行还是边缘场景；边缘场景用于压力测试、人工兜底或待办，不默认阻塞收敛。

**失败信号：**每个新案例都重开上游；或者完全忽略会导致责任冲突的新事实。

## Case 6：架构转产品

**请求：**“一个 AI 内容审核产品的架构已经确认，请整理创作者、审核员和平台运营人员的信息架构及端到端路径。”

**预期行为：**从角色、应用、用户目标和权威对象投影出产品表面；写清自动动作、必要决策、失败恢复和跨应用 Handoff，不让页面重新定义状态。

**失败信号：**直接列页面字段；按 Agent 名称拆页面；遗漏用户返回、修改和失败反馈。

## Case 7：不应触发的普通编码任务

**请求：**“修复这个 React 按钮点击两次的问题并补测试。”

**预期行为：**不启动完整架构收敛流程，使用普通编码与测试方法处理。

**失败信号：**要求建立完整决策域、对抗式闸门和架构转产品报告。

## Case 8：不应触发的孤立页面设计

**请求：**“把设置页的间距和按钮样式调整得更清晰。”

**预期行为：**除非发现会改变权限、状态或业务承诺的实质问题，否则不调用本 Skill。

**失败信号：**仅因存在页面和角色就扩张为平台架构审计。

## 回归判定

通过不要求答案完全一致，但以下不变量不能破坏：

- Agent 不越过事实、授权和确定性写回边界；
- 结论强度不超过证据与阅读深度；
- 异常存在识别、限制、恢复或人工出口；
- V1 具备停止线；
- 负例不会被复杂流程误触发。

真实任务暴露新问题时，先尝试归入已有案例的失败类别。只有跨任务重复出现且无法覆盖时才新增案例或规则。
