# 历史决策审计

用于回看旧 PRD、架构、实现、Decision 或已确认结论。目标是让结论强度与实际阅读深度匹配，并避免重复讨论或错误重开。

## 审计层级

| 层级 | 可以得出的结论 | 不能宣称 |
| --- | --- | --- |
| 目录 / 标题 / 关键词扫描 | 候选问题和精读范围 | 全文审计完成 |
| 定向核验 | 某段原文的直接冲突、歧义或实现差异 | 整个模块失败 |
| 模块精审 | 当前模块结构、上下游和重开建议 | 未读取领域的完整状态 |
| 完成闸门 | 已回写、验证并通过收敛检查的完成状态 | 实现或商业结果完成 |

## 工作步骤

1. 声明回溯目的、覆盖范围、阅读深度和未核验部分。
2. 识别权威层级、版本、状态、日期和明确取代关系。
3. 保留可定位的原文语义，不先强化改写再宣称冲突。
4. 分别标记：`not_reviewed / candidate_issue / direct_conflict / wording_ambiguity / implementation_mismatch / verified_consistent`。
5. 建议结构性重开前，精读模块正文、上层原则、版本边界、相关 Accepted 决策和直接上下游。
6. 提交依据、影响、保留项、候选方案、推荐理由和不确定性。

## 已确认问题重新出现时

先判断：

- `new_fact`：出现会改变结论的新事实，可以重开；
- `implementation_infeasible`：实现验证证明责任或约束无法成立，可以按影响范围重开；
- `edge_scenario`：只是新增边缘场景，用于压力测试或进入待办，不阻塞收敛。

不要因为换了术语、例子或表达方式就重新推导同一问题。

## 输出要求

区分：已经 Accepted 且回写、双方认可但未回写、待用户决策、待实现、待外部验证和当前版本不做。文档存在不等于结论有效，代码存在也不自动获得产品权威。
