# Handoff 与生命周期审查

用于跨模块流程、版本传递、状态变化、外部动作、失败和恢复。目标是发现“模块内部看似完整，但交接后出现死路”的问题。

## Handoff 模板

每条关键交接至少记录：

| 要素 | 必须回答 |
| --- | --- |
| 上游输出 | 具体对象、事实、版本或事件是什么 |
| 合法输入 | 下游接受的前置条件和适用范围 |
| 权威与责任 | 谁拥有对象，责任是否发生转移 |
| 版本与快照 | 使用当前版本、正式版本还是交易时快照 |
| 执行动作 | 是 Query、Command、Task、Decision 还是外部 Action |
| 成功回执 | 什么证据证明交接真正完成 |
| 失败出口 | 拒绝、超时、结果未知、部分成功如何处理 |
| 恢复 | 重试、补偿、后继任务、人工或重新决策如何触发 |

优先检查 3–5 条会改变责任、资金、公开承诺、权益或外部副作用的关键 Handoff。

## 生命周期走查

不要只从对象创建开始。向前追溯触发事件、输入条件和责任来源，向后检查：

```text
触发
→ 候选 / 草稿
→ 校验与必要确认
→ 正式版本
→ 启用或执行
→ 运行与数据回流
→ 修改 / 替换
→ 暂停 / 下线
→ 恢复 / 归档 / 删除
→ 历史与受保护义务
```

不是每个对象都需要全部阶段。应根据对象责任建立自己的生命周期，不能机械复用其他模块状态。

## 异常覆盖

至少检查：失败、超时、用户未响应、取消、重复、并发、部分成功、外部结果未知、迟到事件、争议、删除、恢复和历史版本。

检查目的不是穷举异常，而是确认每类异常都有：

- 可识别事实；
- 最小影响范围；
- 不误报成功的状态；
- 合法恢复或人工出口；
- 历史证据和审计。

## 反例

- 异常分支生成 Todo 或 Decision 后没有回到主链；
- 上游仍可修改，但下游已经按旧版本对外执行；
- 一个“暂停”同时关闭页面、订单、售后和历史查询；
- 超时后直接重发可能已经生效的外部动作；
- 删除当前对象时清除了仍需处理的交易或买家权益。
