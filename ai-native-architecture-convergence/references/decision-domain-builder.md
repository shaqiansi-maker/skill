# 决策域构建

用于新议题、复杂模块或讨论范围不清时。目标是建立足以防止结构性遗漏的问题空间，而不是穷举页面、字段和场景。

## 构建方法

1. 写清近期用途：当前结论将支持什么产品、技术、运营或外部验证动作。
2. 定义核心问题和业务结果，避免从已有功能、页面或 Agent 名称反推需求。
3. 识别对象与粒度：哪些对象能够独立确认、版本化、执行、恢复或追溯。
4. 按当前议题选择决策维度。常见维度包括主体、对象、阶段、权威、状态、版本、输入输出、权限、证据、异常、持久化和演进，但这些不是固定清单。
5. 指明维度之间的正交关系，避免把多个判断压成一个状态。
6. 设置 `unknown / other / needs_review` 的处理方式和责任方。
7. 按依赖关系优先，其次按风险、价值、紧急度、复杂度和验证成本排序。

## 覆盖检查

一个决策域至少要说明：

- 包含什么、排除什么；
- 为什么这些维度能够覆盖当前问题；
- 哪些是封闭枚举，哪些是开放分类；
- 新类型如何进入，而不是由 Agent 自由扩展权威定义；
- 哪些未知会阻塞，哪些可以降级或人工处理；
- 什么时候停止继续拆分。

## 反例

- “先集中讨论两件事”但没有先展示完整范围；
- 把用户列举的几个场景写成全部边界；
- 因为模块复杂而整块删除，而没有拆出 V1 最小承载；
- 用一个 `status` 同时表示生命周期、风险、公开和执行结果；
- 为了显得完整，持续增加低价值边缘场景。

## 推荐输出

输出一张决策域表：`维度 / 必须回答 / 权威来源 / 结论强度 / V1 停止线`，随后说明排序理由。若当前只处理其中一部分，明确它在完整决策域中的位置。
