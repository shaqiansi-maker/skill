# 权威与分层审计

用于涉及 Agent、自动执行、权限、业务事实、外部结果或写回的议题。目标是防止“模型能够理解”被误写成“模型有权决定”。

## 基础分层

| 层级 | 主要责任 | 不应承担 |
| --- | --- | --- |
| 观察与输入 | 保存用户输入、系统事件、外部响应和来源 | 自动升级为已确认事实 |
| Agent 候选 | 语义理解、归类、推断、规划和建议 | 直接写资金、权限、承诺或正式状态 |
| Verification / Policy | 校验证据、版本、权限、风险、契约和适用范围 | 冒充业务执行成功 |
| Domain Service / Write-back | 执行合法状态转换、幂等、事务、外部动作和权威写入 | 让页面、Prompt 或人工绕过规则直接改表 |
| 人类决策 | 提供专属事实、价值判断、责任确认、风险接受和外部副作用授权 | 被 Agent 静默代替 |

具体系统可以增加层级，但必须保持事实、候选、授权、执行和结果可区分。

## 每个关键结论必须回答

- 观察到了什么，来源是什么？
- 哪些是事实、推断、授权、状态、风险或结果？
- 谁拥有权威对象？
- 谁可以提出候选，谁最终判断？
- 谁能写入，写入需要什么版本和幂等身份？
- 如何验证写入成功与外部动作真实结果？
- 失败、超时、冲突和结果未知如何保存？
- 人工介入时使用什么权限和审计路径？

## 持久化边界

开放分类不等于自由文本直接成为权威枚举。通常采用：

```text
结构化来源事实
→ Agent 候选判断
→ Verifier / Policy 决定可用范围
→ Domain Service 写入权威对象或受限 Evidence
```

原始输入、候选、判断依据、最终决策和执行结果应能关联，但不要复制完整敏感信息到每个任务对象。

## 常见混淆

- 证据来源等级被当成事实真实性；
- 授权允许被写成动作成功；
- HTTP 成功被写成外部业务成功；
- Agent Profile 名称被当成权限；
- UI 可见性被当成服务端授权；
- Operator 人工处理被当成数据库旁路；
- `unknown` 被强行归入成功或失败。
